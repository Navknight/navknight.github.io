Two small games, each a minute or so, about the systems ideas I work with: caches and prefetchers, and what happens to latency as a backend fills up.

Beat the cache oracle

What this teaches: replacement policy only matters when data gets reused, and a good prefetcher can beat even the optimal replacement policy.

This is the problem my research on DAP (Dead-block Aware Prefetching) tackles: predict which cached blocks will never be used again and put prefetches there instead of over live data. That cut GPU cache misses by 32%.

A 4-set, 2-way cache with 64-byte lines receives a stream of memory addresses. You choose a replacement policy (LRU, FIFO or random) and a prefetcher (none, next-line or stride), then step through one of three access patterns: sequential, strided and a loop with reuse. Hits and misses are shown line by line with a live hit-rate meter, and your final score is compared against Bélády’s optimal replacement policy. Enable JavaScript to play.

Scale the backend

What this teaches: queueing delay grows like 1/(1−ρ), so latency is flat until a tier nears full utilisation and then shoots up. Find the bottleneck and fix it before that happens.

Traffic to a web backend ramps up over 60 seconds, with a spike near the end. Served requests earn credits, which you spend on app replicas, a Redis cache (a longer TTL gives more hits but staler reads), an async queue, database read replicas and a rate limiter. Each tier is modelled as a queue: latency grows as 1/(1−ρ) with utilisation ρ, and requests drop once ρ reaches 1. The goal is to keep p99 latency under a 300 ms SLO with almost no errors; a live sparkline tracks latency and throughput, and a summary grades your run. Enable JavaScript to play.
